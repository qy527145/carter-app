# 团队协作协议（v1）

`.carter/` 团队目录里有两类数据，存法不同：

| 类别 | 例子 | 存在哪 | 合并语义 |
|---|---|---|---|
| **状态** | 目标、任务、成员、看板 | `.carter/` 下的 JSON / HTML 文件，**随代码分支走** | 最后写的赢；冲突由 git 照常处理 |
| **事件** | 评论、@、广播、指派、认领 | 一条独立的 ref `refs/carter/events` 上的提交链 | 只追加，永不冲突 |

本文规定「事件」这一半的格式，以及「成员」这份状态的格式。任何实现（本应用、
`carter-team` 脚本、将来的机器人）只要按这里写，就能互相读懂。

---

## 1. 事件存在哪

### 1.1 独立的 ref，不在代码分支上

事件**不**打在当前分支上，而是追加到 `refs/carter/events`：

```
refs/carter/events                      本地的事件链（自己写的 + 已合并的）
refs/carter/remotes/<remote>/events     上次从远端拉到的那份
```

理由：

* **送达与分支无关。** 你在 `feature/x` 上 @ 张三，张三在 `main` 上也要立刻看到。
  打在分支上的话，合并之前他永远看不到。
* **不污染代码历史。** PR 里不会多出一串 `carter/comment` 提交；squash 合并也不会
  把讨论压没。
* **推送冲突可以自动解决。** 事件只追加、彼此独立，推送被拒时取回远端那份，把自己
  的新事件重新接到它后面再推即可（见 1.3），不需要人介入。

每条事件是一个**空树提交**：tree 固定为 git 的空树 `4b825dc642cb6eb9a060e54bf8d69288fbee4904`，
不碰工作区、不碰索引、不碰任何分支。用 `git commit-tree` 生成，用
`git update-ref <ref> <new> <old>` 做比较并交换地写入。

### 1.2 读

读事件 = 把下面几处的提交并起来，按 SHA 去重，按提交时间倒序：

1. `refs/carter/events`
2. `refs/carter/remotes/*/events`
3. **当前分支上的旧事件**（v0，见第 5 节）—— 只读，不再往这里写

只认提交信息里带 `Carter-Team:` 那一行的提交。

### 1.3 写与推送

```
写：  new = commit-tree EMPTY_TREE -p <本地 tip> -m <message>
      update-ref refs/carter/events new <本地 tip>       # 比较并交换，防止本机并发写

推：  push <remote> refs/carter/events:refs/carter/events
      被拒（非快进）→
        fetch <remote> +refs/carter/events:refs/carter/remotes/<remote>/events
        把「本地有、远端没有」的事件，按原顺序逐条 commit-tree 接到远端 tip 后面
        （作者、作者时间、提交信息原样保留，只换父提交）
        update-ref 本地 tip → 新链尾，再推
      最多重试 3 次
```

因为每条事件只是一段提交信息，重新接到别人后面不改变任何语义 —— 这就是
「永不冲突」的来源。SHA 会变，所以**事件之间不要靠 SHA 互相引用**，要引用就用
`ref=` 字段（见 2.3）指向一个稳定的事件 id。

### 1.4 拉

```
fetch <remote> +refs/carter/events:refs/carter/remotes/<remote>/events
```

拉下来不需要合并：读的时候本来就把本地与远端两份并起来（1.2）。只有在推送时
才需要把两条链接成一条（1.3）。

> 注意：`git clone` / 普通 `git fetch` **不会**带上 `refs/carter/*`，必须显式拉。
> 客户端的同步与观察员都会做这一步；只用命令行的人可以加一条 refspec：
> `git config --add remote.origin.fetch '+refs/carter/events:refs/carter/remotes/origin/events'`

## 2. 一条事件长什么样

```
carter/mention t-1a1a0801ce8-56113 → 张三           ← 抬头：给人看，git log --oneline 一眼能读

接口字段定好了，你那边可以开始联调。                 ← 正文：自由文本，可多行

Carter-Team: v=1 kind=mention id=t-1a1a0801ce8-56113 goal=g-1a1a07ff9c0-46685 from=m-xq to=m-zs via=carter eid=e-1a1b2c3d4e5-ab12
```

### 2.1 Trailer 字段

最后一行 `Carter-Team:` 之后是空格分隔的 `key=value`。值里**不能有空格**；需要
多个值时用逗号（`to=m-a,m-b`）。

| 字段 | 必填 | 说明 |
|---|---|---|
| `v` | 是（v1 起） | 协议版本。缺省按 0 读（第 5 节） |
| `kind` | 是 | 事件种类，见 2.2 |
| `eid` | 是（v1 起） | 事件自己的稳定 id，`e-<base36 毫秒>-<4 位随机>`。重新接链（1.3）后 SHA 会变，`eid` 不变 |
| `from` | 是（v1 起） | 发出者的成员 id（`m-…`，第 3 节） |
| `id` | 视 kind | 事件的对象：任务 `t-…` / 目标 `g-…` / 看板 `b-…` |
| `goal` | 否 | 对象所属的目标，方便按目标过滤 |
| `to` | 视 kind | 收件人成员 id，逗号分隔；`*` 表示全员 |
| `via` | 否 | `carter` = 由 agent 代发。界面上标「经卡特」 |
| `ref` | 否 | 回复 / 引用的另一条事件的 `eid` |
| `due` | 否 | 期限，毫秒时间戳。`request` 用 |

作者与时间取提交本身的 author，不在 trailer 里重复。

### 2.2 事件种类

| kind | 用途 | 对象 `id` | 收件人 `to` | 正文 |
|---|---|---|---|---|
| `comment` | 对任务 / 目标说话 | 必填 | 可选（附带 @ 时） | 必填 |
| `mention` | @ 某人，可以带上任务 | 可选 | 必填 | 必填 |
| `broadcast` | 全员通知 | 可选 | `*` | 必填 |
| `request` | 请人做一件需要回应的事（评审、拍板） | 可选 | 必填 | 必填；可带 `due` |
| `assign` | 把任务指派给某人 | 必填 | 新负责人 | 可选（说明） |
| `handoff` | 负责人把任务转交给别人 | 必填 | 新负责人 | 可选 |
| `claim` | 自己认领一个任务 | 必填 | — | 可选 |
| `release` | 释放认领 | 必填 | — | 可选 |
| `join` | 成员加入团队 | — | `*` | 可选（自我介绍） |
| `note` | 进度汇报 | 可选 | — | 必填 |
| `sync` | 同步握手（观察员跑通时） | — | — | — |

`assign` / `handoff` / `claim` / `release` 会**同时改任务文件**里的 `assignee`。事件是
「谁在什么时候、为什么这么改」的记录，任务文件是「现在归谁」的状态。两者不一致时
以任务文件为准。

### 2.3 正文里的 @

正文里可以写 `@昵称`，便于人读。但**收件人只看 `to=` 字段**，不从正文里解析 ——
昵称会改、会重名，id 不会。客户端在发送时把 `@昵称` 解析成 id 填进 `to=`。

### 2.4 向前兼容

* **不认识的 `kind`**：照常显示成一条普通消息（抬头 + 正文），不丢弃。
* **不认识的字段**：忽略，但不要在重写时删掉（1.3 原样保留提交信息）。
* **`v` 比自己高**：照上面两条读；界面可以提示「有新版客户端写的消息」。

## 3. 成员

### 3.1 存法

一人一个文件：`.carter/members/<member-id>.json`。

```json
{
  "schema_version": 1,
  "kind": "member",
  "id": "m-1a1b2c3d4e5-ab12",
  "name": "徐侨",
  "emails": ["xu.qiao@kotei.com.cn", "wmymz@icloud.com"],
  "role": "",
  "joined_at": 1793690000000
}
```

* **一人一个文件**：两个人同时加入改的是两个不同的文件，不会冲突。
* **`emails` 是数组**：同一个人在公司机器与个人机器上的 git 邮箱常常不同。
  比较时一律转小写。
* **成员文件是状态，跟着代码分支走。** 新成员加入后要像任务一样提交并推送，
  别人同步之后才能指派给他。

### 3.2 认人

本机的 git `user.email`（小写）落在哪个成员的 `emails` 里，本机就是那个成员。
找不到就是「还没加入」。

### 3.3 加入

客户端第一次在这个团队里需要身份时（打开团队页、发消息、认领）：

1. 用本机 git 邮箱查成员表，查到了直接用。
2. 查不到时弹出「在这个团队里怎么称呼你」，预填**客户端的全局昵称**（应用设置里的
   `nickname`，没有就用 git 的 `user.name`）。同时列出已有成员，提供「我是 X，
   这是我的另一台机器」—— 选了就把本机邮箱追加进 X 的 `emails`，不新建成员。
3. 写成员文件、提交（只提交 `.carter/members/`），再发一条 `join` 事件。

同名时提示，但不阻止：成员靠 id 区分，昵称只是显示用。

### 3.4 引用

任务的 `assignee`、目标的 `owner`、事件的 `from` / `to`，一律存**成员 id**。

v0 的数据里存的是 `名字 <邮箱>`。读的时候两种都认：是 `m-` 开头就按 id 查，否则按
邮箱匹配到成员（匹配不上就原样显示那个名字）。**写的时候只写 id。**

## 4. 送达与同步（观察员）

客户端初始化团队（或配好远端）时会建两条观察源：

| 源名 | 命令 | 间隔 | 做什么 |
|---|---|---|---|
| `<团队> · 团队消息` | `carter:team-inbox` | 1 分钟 | 拉取远端事件（1.4）、读出事件（1.2）、只输出**跟我有关**的那些 |
| `<团队> · 团队同步` | `carter:team-sync` | 5 分钟 | 拉消息、推消息、推分支、能快进就快进 |

两条都是内置命令（`carter:` 前缀不交给 shell），三平台行为一致。消息源**不碰工作区**，
所以写代码期间照样收得到；同步源管的是分支状态，工作区脏的时候只推不拉。

「跟我有关」是：

* `to` 里有我，或 `to=*`；
* 我负责的任务上的 `comment` / `handoff` / `assign`；
* 不是我自己发的。

观察源按行去重，只把新出现的行交给卡特助理判断要不要开工单（例如收到 `request`
就开一张「张三请你评审 t-xxx」）。同步源正常时**不输出任何行**，只在没同步成时
说一句原因 —— 否则每五分钟就会多一条噪音。

### 4.1 什么时候真的推上去

写事件时立刻推（1.3）。`.carter/` 里的状态（目标 / 任务 / 成员 / 看板）走另一条路：

* **提交**：一轮对话结束时收成一条提交；界面上点的指派 / 认领 / 改状态立刻提交。
* **推送**：提交之后马上在后台推一次；五分钟的同步源还会再试。
* **边界**：只在远端没动、这次推送一定被接受时才推；本地落后就先只做快进（工作区
  干净时）；两边各有新提交（真分叉）时什么都不动，把原因说出来，等人工合并。

后台自动跑的东西不产出冲突 —— 这是两条通道共用的原则。

## 5. v0 兼容

v1 之前的事件直接打在代码分支上，trailer 没有 `v` / `eid` / `from`：

```
Carter-Team: kind=comment id=t-1a1a0801ce8-56113 goal=g-1a1a07ff9c0-46685
```

处理方式：

* **读**：继续从当前分支的历史里读（1.2 第 3 条），`v` 按 0、`eid` 用提交 SHA 代替、
  `from` 按作者邮箱匹配成员。
* **写**：只写到 `refs/carter/events`，不再往分支上打空提交。
* 不搬迁旧事件：它们已经在代码历史里，搬一份到事件 ref 上只会让同一条消息出现两次。
