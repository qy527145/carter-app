# carter-app

Tauri + React 桌面 agent 客户端。底层复用 **carter**（agent harness）与 **llm_adapt**（线协议底座）。

## 它是什么

一个能自己跑工具的对话客户端，同时把「模型看到的原始报文」摊开给你看。四件事：

1. **三种线协议原生支持** —— Anthropic Messages / OpenAI Chat Completions / OpenAI Responses。
   渠道按自己声明的协议说话，不做有损归一化。
2. **模型原生的远程工具** —— Anthropic 的 `web_search`、Responses 的 `web_search` 等由厂商自己
   执行。渠道不支持时**明确报出来**，不会静默丢掉让你以为开了。
3. **思考 / 工具 / 多模态统一抽象** —— 走 llm_adapt 的 IR：思考签名、工具结果里的图片、
   认不出的服务端工具块都保得住，块与块的顺序也保得住。
4. **原始报文检视** —— 对话里任意一轮，都能查到产生它的那次 HTTP 请求。
   「可视化」一页把字节**解回 IR** 之后按语义摊开（系统提示词、工具清单、上下文、
   回答与思考、token），「格式化」一页把请求与响应分开摊成结构化 JSON（响应是流式的
   话，就是一串排开、各自美化的 SSE 事件），「原始」一页是不做任何改动的字节。

## 结构

```
crates/carter-app-core/   应用核心：会话编排、事件桥、状态根、报文捕获
                          刻意不依赖 Tauri —— 能脱离 webview 测
src-tauri/                薄薄一层：Tauri 命令 + 事件转发
src/                      React 前端
```

依赖方向是单向的：

```
React ──▶ src-tauri ──▶ carter-app-core ──▶ carter ──▶ llm_adapt
```

`carter` 与 `llm_adapt` 直接从 crates.io 引入（`carter = "0.1.4"`、`llm_adapt_core = "0.1.0"`）。
两个 crate 同属这个作者，发布前先在各自仓库里改、发布后再升版本号。

## 跑起来

```bash
bun install
bun tauri dev
```

第一次跑需要至少一个渠道。可以直接在**设置 → 渠道**里新建（界面会写回
`~/.carter/config.toml`），也可以先在文件里配好：

```toml
[providers.anthropic]
kind = "anthropic"
api_key = "${ANTHROPIC_API_KEY}"
server_tools = ["web_search"]      # 可选：让模型自己联网搜索

  [providers.anthropic.models.sonnet]
  meta = "anthropic/claude-sonnet-4-5"
```

完整配置说明见 carter 仓库的 `config.example.toml`。会话、技能、记忆与 carter CLI 共用
`~/.carter/`；客户端独有的数据（原始报文捕获、界面设置）落在 `~/.carter-app/`。

## 输入框里能做什么

| 输入 | 行为 |
|---|---|
| `/` | 弹出命令菜单。内置命令（`/new` `/model` `/cwd` `/fork` `/btw` `/goal` `/export` `/settings` `/help`）由本应用执行 —— **从菜单点、或者直接打出来回车都一样**；`~/.carter/commands/*.md` 里的自定义命令按回车后由后端展开成 prompt |
| `@` | 弹出文件菜单（按工作目录里的路径模糊匹配）。发送时把文件内容按 `--- path ---` 包裹成上下文块注进去，超过 128 KB 的文件只给路径让模型自己读 |
| 粘贴图片 | 存进 carter 的内容寻址图片库（sha256 去重 + 长边压到 1568px），消息里只留 `[img:hash.ext]` 引用 —— 会话文件保持纯文本 |
| 点模型名 | 下拉切换本会话的模型（按渠道分组） |
| 点工作目录 | 原生目录选择器。换目录**会新开一个会话**：carter 的会话按 cwd 分文件存，换目录在磁盘上就是另一条对话 |

斜杠命令与 `@文件` 的展开都在**后端**做，不在输入框里 —— 展开后是几百行文件内容，
摆在输入框里给用户看着它发出去没有意义。这也让 GUI 与 CLI 走同一套规则
（自定义命令用 carter 的 `commands::expand`，图片用 `media::inline_user_attachments`）。

**模型正在干活时也能继续说话。** 发出去的消息进「排队中」，这一轮一结束就依次处理；
`Enter` 排队，`⌘/Ctrl+Enter`（或排队条上的「插队」）会中断当前这一轮、把这条提到最前。
点「停止」是**立刻**生效的：正在跑的 shell 命令会被连同子进程一起杀掉，不会等它
跑满超时。会话任务意外退出（窗口重开、上一轮被强制中断）时，发下一条消息会自动
按磁盘上的历史重建会话，界面不会停在一条「发不进任何东西」的对话上。

## 长任务目标与侧边聊天

两个斜杠命令，对应两种以前做不了的用法。

**`/goal <目标>` —— 挂住一个目标，让模型接着干。** 说完「把这个仓库的告警清零」就撒手，
模型停下而目标未完成时，本应用会自己追加一轮「继续」推着它走，界面上每多推一轮就多一条
「自动继续」的分隔条。目标条上有暂停 / 继续 / 编辑 / 完成 / 清除。模型想收工时调用
`goal_update` 说明是完成了、被卡住了、还是需要你拍板 —— 「需要拍板」会把它问的问题显示在
目标条上，而不是让它自己把「要不要删这个文件」拍掉。

**`/btw <随口一问>` —— 侧边聊天，不动主对话。** 主对话正在跑长任务时，想插一句
「顺便问下，`SessionHandle` 是干嘛的」：右边滑出一个抽屉，它**继承主对话的历史作为参考**
（折叠在顶部，默认不展开），独立并发跑，主对话的流式输出照常继续。关掉抽屉即丢 ——
它不落盘、不进侧栏、不进报文面板，也不会把这句话留在主对话的上下文里。

两条都不需要额外配置。`/goal` 的状态存在 `~/.carter-app/goals/<会话 id>.json`，
`/btw` 什么都不存。

## 工具

内置工具**不是** carter 那套原样搬过来的 —— 有两个换成了本应用的实现：

- **`bash`** 跨平台。carter 那个硬编码 `sh -c`；从资源管理器或 IDE 启动时 PATH 常被
  精简（Git for Windows 只把 `Git\cmd` 写进 PATH，那里有 `git.exe` 却没有 `sh.exe`），
  于是模型每次调用都拿到 `failed to spawn command` 而且看不出原因。现在会按
  PATH → 常见安装位置探测 POSIX shell，找不到才退回 `cmd /C`，并且**把探测结果写进
  工具描述** —— 模型看不到我们的进程环境，只能从描述里知道该写 `ls` 还是 `dir`。
  另外 `bash` 显式跑在会话的 cwd 里（桌面进程的 cwd 取决于从哪启动，与会话的 cwd
  不是一回事），Windows 上还会按 OEM 代码页解 `cmd` 的中文输出。
  用户点「停止」时命令会被立刻杀掉（独立进程组，整棵树一起收）；起服务、跑长构建
  这类命令写 `run_in_background: true`，立刻拿回一个 `shell_id`，之后用
  `bash_output` 读增量输出、`kill_shell` 结束它 —— 不把整轮对话卡在一条命令上。
  **正在跑的那张 bash 卡片上还有两颗按钮**：「中断命令」只结束这一条（模型会拿到
  「已中断」的结果接着往下走，不等同于整轮停止）；「转后台」让命令继续跑，工具立刻
  返回 `shell_id`，已经产出的输出也写进日志。
- **`ask_user_question`** 一次问一组问题，支持多选、选项可带说明。carter 那个一次
  只能问一个：三个问题就是三轮完整的模型往返，而且用户看不到全貌就没法做取舍。

- **文件工具**（`read_file` / `write_file` / `edit_file` / `glob` / `grep`）包一层
  `CwdScoped`：把相对路径按**会话的**工作目录解析。carter 那五个工具直接
  `Path::new(&path)`，相对路径落到**进程的** cwd 上 —— 命令行下这是对的，桌面应用下
  必然错（进程 cwd 取决于从哪启动），而且它不报错：系统提示里写着「工作目录：…」，
  文件却读写到了别处。`~` 也一并展开（`std::fs` 不认 `~`）。
  `save_memory` 的**项目级**作用域同理但没法靠改参数救（目标路径是它内部按 `scope`
  算的，而 `scope` 的默认值就是 `project`），所以直接**明确拒绝**并提示改用
  `scope = "global"` 或 `write_file` —— 写错地方的记忆比没有记忆更坏。

其余工具（`grep` / `todo_write` / …）沿用 carter 的实现，但外面套了一层
**记录包装**：carter 的 UI 事件只带截断的参数与「结果第一行 120 字符」，数据不够就只能
给所有工具画同一种卡片。包装层把完整的参数、结果与耗时送给界面，于是每种工具能按
自己的习惯呈现 —— bash 显示命令与输出、`todo_write` 显示清单、`edit_file` 显示改动前后、
`grep` 显示命中数。底栏的待办进度在全部完成后 6 秒自动收起。

## 界面里能配什么

| 页 | 能做什么 |
|---|---|
| 渠道 | 增删改 `[providers.*]`：协议、Base URL、API Key、服务端工具、模型列表 |
| 模型 | 全部 `渠道/模型` 一览（上下文窗口、能力、定价来自 models.dev）、增删改、设主模型与**副模型** |
| 工具 | 内置工具的启用/禁用（**只对本应用生效**，见下） |
| 技能 | 查看 / 新建 / 编辑 / 启停 / 删除 `~/.carter/skills/*/SKILL.md`；可另加扫描路径（Claude Code / Codex 预设或自定义），取并集 |
| MCP | 增删改 `[mcp.servers.*]`（stdio / http） |
| 会话 | 全部会话、全文搜索、重命名、fork、导出、删除 |
| 外观 | 浅色 / 深色 / 跟随系统、侧栏宽度 |
| 关于 | 路径速查与「哪些事还只能在文件里做」 |

改完即时热重载：正在跑的会话从**下一条消息**起用新配置。唯一的例外是 MCP ——
server 是会话建立时连的，改完要新开一个会话。

## 几个不显然的设计

**一个会话一个 tokio 任务。** `Thread` 是可变的、且一轮会连着跑很多次模型调用。
放进共享循环就得给每个会话加锁，而锁还要跨 `await` 持有 —— 一个会话卡在上游网络上，
别的会话全被堵住。一任务一会话天然隔离，并发量就是会话数。

**生成中只接受「取消」、「作答」与「`/goal` 动作」三条命令**，其余排队等这一轮结束。
否则一个还在等上游网络的轮次会把取消按钮也堵住；而 `/goal pause` 尤其不能等 ——
用户按暂停正是因为不想再等自动继续跑下去了。

**事件按会话分包。** 多个会话可以同时跑，事件里带 `session_id`，前端按会话分桶渲染，
不会把两个对话的增量混进同一个气泡。

**text 与 thinking 是**有序的兄弟条目**，不合并成一个字段。** 模型会交错输出，
合并就还原不出顺序 —— 而回灌历史时顺序是硬要求（Anthropic 要求 thinking 块排在最前，
且签名原样回传）。

**报文捕获存 JSONL 而不是 SQLite。** 数据天然按会话分片，查询只有「按会话取全部」
和「按 id 取一条」两种，扫描一个文件与走一次索引没有可感差异；换来的是零额外依赖，
且文件能直接拿编辑器打开 —— 排障时最想做的事就是这个。

**图片不随历史存 base64。** 一张图几百 KB，直接进会话 JSONL 会把文件撑爆。
历史里存的是 `[img:<hash>.<ext>]` 引用 token，真发出去时才去媒体库取字节。

**改配置走 '定点编辑 TOML'，不是「读进来再全量写回」。** `carter::config::Config` 是
Deserialize-only，而且 `Config::load()` 会先对整份文本做 `${ENV_VAR}` 插值 —— 全量重
序列化会把用户写的 `api_key = "${ANTHROPIC_API_KEY}"` 换成**明文密钥**写进磁盘。
所以界面用 `toml_edit` 在原始文本上只动被改过的那几个键：注释、格式、未知字段与
`${VAR}` 字面量全部原样留下。写盘后再 `Config::load()` 验一次，读不回来就还原上一版。

**工具开关只对本应用生效，而且界面上写明了这一点。** carter 0.1.4 的 `ToolRegistry` 是
「全部常开」、`Config` 里也没有开关字段，所以本应用在 carter 装配完之后自己筛一遍
（`crates/carter-app-core/src/tools.rs`），名单存在 `~/.carter-app/settings.json`。
carter 命令行读不到它 —— 把这条藏在心里、「关了但只在 GUI 里关」是比不做更坏的结果。
子 agent 的工具池用的是**同一份筛过的快照**，所以关掉的工具对子 agent 也失效。

**单个技能的启停是把目录搬走。** carter 的 `parse_skill_md` 不认 frontmatter 里的
`enabled` 字段（会被当未知键静默忽略），所以启停落在文件系统上：目录在
`~/.carter/skills/` 与 `~/.carter/skills.disabled/` 之间搬，可逆且不丢内容。

**技能可以来自多个扫描路径，取并集。** 技能页除了本地目录，还能加额外的**扫描父目录**
（Claude Code 的 `~/.claude/skills`、Codex 的 `~/.codex/skills` 做成一键预设，也可以手填
任意路径），加完取并集：本地优先，按名字去重、先出现者胜。列表**不去重** —— 被同名技能
挡住的那一行也列出来并标明是谁挡的，否则「我 Codex 里那个技能为什么不生效」没法回答。
外部路径是别人的目录，所以那边的技能**只读**：开关走「按名字忽略」，编辑与删除按钮不出现。

两个坑写在这里免得再踩：Codex 的技能在 `~/.codex/skills/.system/` 的**下一层**，所以它的
预设一次给两条路径（页面上会显示「子目录 1 / 技能 0」，一眼看出是层级问题）；Codex 的
frontmatter 写成 `name: "imagegen"`，而 carter 的解析器不去引号 —— 直接照抄会得到一个带
引号的名字，而 `skill` 工具是按**目录名**找文件的，那些技能会「列得出来、永远加载不到」。
所以本应用这一层统一以目录名为身份、并褪掉成对的引号。

**自动继续必须有闸。** 目标模式下「模型停下 → 再推一轮」是个闭环，而闭环的反面是
死循环。所以除了模型自己报的结局，还有四条：用户点过停止（**用户的中断永远优先**，
把「停止」变成假的比不做自动继续更坏）、这一轮出错（对着正在失败的上游重试等于把一次
故障放大 20 倍）、连续两轮一个工具都没调（只是在说话，不是在干活）、以及连续 20 轮的
硬上限。判定整块是个纯函数（`goal.rs::decide_after_turn`），每条规则各有一测。

**侧边聊天的历史要截到「干净边界」。** 中途被取消的一轮，历史尾部可能挂着一个没有结果的
`tool_use`，或者停在一条 `tool_result` 消息上。原样种进侧边会话，前者会被上游以
「tool_use 无对应 tool_result」直接 400，后者会让紧接着的用户消息变成连续两条 user
（llm_adapt 的 anthropic codec 是逐条映射、不合并的）。所以只种到**最后一个不含工具调用
的 assistant 消息**为止（`side.rs::truncate_to_clean`）—— 报错的还是侧边那条对话，
用户完全看不出跟主对话有什么关系。

**关会话要显式通知，光从注册表里拿掉不算。** `SessionHandle` 持有命令通道的发送端，
而会话任务又攥着一个 `Arc<SessionHandle>` —— 于是 `cmd_rx.recv()` 永远不会返回 `None`，
任务（连同 MCP 子进程）永远不退出。现在 `close_session` 会 `close.set()` + `cancel.set()`，
并级联关掉挂在它上面的侧边会话。`/btw` 的「关掉即丢」正是靠这条成立。

**报文面板显示的是「模型实际收到/说出的话」，不是对字节的另一套解读。** 解码走
`llm_adapt` 的 codec（`inspect.rs`：`decode_request` / `decode_response` /
`new_stream_decoder` + `BlockAssembler`），与真实链路**同一套代码**。所以协议层要是
把哪个字段丢了（`reasoning_content` 之类），这一页也会一起没有 —— 那正是应该被发现的事；
反过来，前端另写一份「猜」的解码，显示的就不是模型看到的东西，面板也就没有意义了。
协议存在每条抓包记录里（会话建起来时从渠道配置取），老记录按 URL 兜底猜并**标明是猜的**。

**进行中的请求从「发出」那一刻就可见，列表与详情都标着上游渠道。** 请求还没收到响应时，
URL、渠道、模型与请求体就已经确定了 —— 抓包钩子在 `before_request` 就建档（`capture.rs`
的 pending 表），列表每秒取一次，所以这里看到的是「此刻正在发生什么」，而不是等首字甚至
等收完。渠道（`[providers.X]` 的 X）必须单独记：同一个模型可以配在多个渠道上，中转常把
域名配得和官方一样，事后光看 URL 分不出来。列表轮询走的是增量维护的摘要缓存，不会每秒
把整份（可能几 MB 的）报文重新解析一遍。

**「查看报文」跟着回答走，而回答要能跨重启对回它的请求。** 每条助手消息带一个用户轮序号
（实时来自 `turn_started`，历史由 `view.rs` 按同一口径算出来），点它就筛到那一轮。
续接会话时这个序号必须**接在历史后面**（`session.rs` 回填 `thread.user_turns`）——
carter 的 `Thread::from_parts` 从 0 重数，照抄会让重启后的第一轮与历史里的第一轮撞号，
一个筛选条件就套住了两条不相干的请求。

**新会话立刻出现在侧栏，标题随后自己长出来。** carter 的会话文件是**惰性创建**的
（`Recorder` 等到第一条消息才建文件），所以刚点「新对话」时磁盘上什么都没有、
列表里也就没有它 —— 界面上表现为「左边什么都没多」。前端于是补一行临时的当前会话
（`store.ts::withCurrent`），第一条消息落盘后由真正的记录换掉。

标题在第一轮**并行**生成（另一条 tokio 任务，不挡这一轮 —— 挡了就是让用户盯着一个
只影响侧栏一行的模型调用）。提示词与后处理用 carter 的 `generate_title`，外面套一层
把 `reasoning_effort: "none"` 塞进请求体的 provider（`title.rs`）：它的 `max_tokens`
是 32，而**推理模型会把这 32 个 token 全花在思考上**，正文一个字都不剩（DeepSeek 实测
`finish=Length`、`content=""`）。关掉思考，32 个 token 对标题绰绰有余，还省一次推理的钱。
这个字段只对**实测认它**的渠道发（目前是 DeepSeek）—— 不认的厂商多一个字段就 400，
那等于把本来能用的标题弄坏。写回时**只写还没有名字的会话**（`auto_title_allowed`）：
用户在这几百毫秒里自己改过名，机器起的名字就不该盖回去。

**副模型是「压缩上下文 / 起标题 / 总结」专用的那个**（配置里的 `agent.fast_model`）。
那些活儿要的是便宜和快，不必用最强的模型。没配就回落主模型。它在会话里解析一次后
缓存住，用户在设置页改了，下一轮自动重解析。
